# 3x-ui روی Railway با یک پورت واحد

این پروژه **3x-ui** (پنل مدیریت Xray) را روی Railway بالا می‌آورد — بدون نیاز به سرور و بدون تنظیمات پیچیده.

مشکل همیشگی Railway این است که فقط به **یک پورت** اجازه‌ی بیرون‌آمدن می‌دهد. این پروژه با یک nginx داخلی، هم پنل و هم اینباندها را زیر همان یک پورت جمع می‌کند. یعنی:

- ✅ پنل مدیریت روی دامنه‌ی شما باز می‌شود
- ✅ چند اینباند جدا (تا ۱۰ تا) همزمان کار می‌کنند
- ✅ ساب‌لینک خودکار
- ✅ IP واقعی کاربران در پنل ثبت می‌شود
- ✅ قابلیت IP Limit فعال است

پنل **خام و خالی** بالا می‌آید — اینباندها را خودتان طبق نیازتان می‌سازید.

---

## قبل از شروع

فقط دو چیز لازم دارید:

1. یک حساب **GitHub** (رایگان)
2. یک حساب **Railway** (رایگان — [railway.app](https://railway.app))

---

## نصب گام به گام

### گام ۱ — چهار فایل را در گیت‌هاب بگذارید

یک ریپازیتوری جدید در گیت‌هاب بسازید (خصوصی هم بشود اشکالی ندارد) و این **۴ فایل** را در ریشه‌ی آن آپلود کنید:

| فایل | کارش |
|---|---|
| `Dockerfile` | دستور ساخت و نصب |
| `start.sh` | اجرای پنل و nginx هنگام بالا آمدن |
| `nginx.conf.template` | مسیردهی ترافیک |
| `auto-sockopt.sh` | تنظیم خودکار IP واقعی |

⚠️ **هر ۴ فایل لازم است.** اگر یکی نباشد، بیلد شکست می‌خورد.

### گام ۲ — در Railway دیپلوی کنید

1. وارد Railway شوید → **New Project**
2. گزینه‌ی **Deploy from GitHub repo** را بزنید
3. ریپازیتوری‌تان را انتخاب کنید (اگر دیده نمی‌شود، یک‌بار به Railway دسترسی گیت‌هاب بدهید)
4. Railway خودش فایل `Dockerfile` را پیدا می‌کند و شروع می‌کند

بیلد اولین بار حدود **۲ تا ۴ دقیقه** طول می‌کشد. منتظر بمانید تا وضعیت **Success** شود.

> اگر Railway گفت Dockerfile پیدا نشد: بروید به **Settings → Build** و در فیلد **Dockerfile Path** بنویسید `Dockerfile`.

### گام ۳ — دامنه بسازید (⚠️ مهم‌ترین قدم)

بروید به تب **Settings → Networking** و **Generate Domain** را بزنید.

**حتماً پورت دامنه را `3000` بگذارید.** اگر پورت دیگری بگذارید، دامنه‌ی شما بالا می‌آید ولی پنل باز نمی‌شود.

| فیلد | مقدار درست |
|---|---|
| Target Port | **3000** |

### گام ۴ — وارد پنل شوید

آدرس پنل شما این است:

```
https://دامنه‌شما.up.railway.app/managepanel/
```

> ✅ **لازم نیست مسیر را تایپ کنید.** فقط خود دامنه را باز کنید — خودکار به پنل می‌رود. هم روی دامنه‌ی `railway.app` و هم روی دامنه‌ی کاستوم.

یوزرنیم و پسورد پیش‌فرض:

```
admin / admin
```

🔐 **همین حالا از بخش تنظیمات (Settings) پسورد را عوض کنید.** پنل شما روی اینترنت باز است.

### گام ۵ — یک Volume وصل کنید (⚠️ قبل از ساخت اینباند!)

بدون این کار، **با هر بار دیپلوی مجدد همه‌ی اینباندها و کاربرها پاک می‌شوند.**

بروید به **Settings → Volumes** و یک Volume بسازید با این مسیر:

```
/etc/x-ui
```

بعد از وصل کردن، Railway یک بار خودش ری‌دیپلوی می‌کند — طبیعی است.

### گام ۶ — اولین اینباند را بسازید

در پنل → **Inbounds → Add Inbound**:

| فیلد | مقدار |
|---|---|
| Protocol | **VLESS** |
| Port | **8080** |
| Network | **ws** |
| Security | **none** |
| Path | مثلاً `/cdn` |
| Listen IP | خالی بگذارید |

سپس داخل همان اینباند یک **Client** اضافه کنید.

> 💡 پورت `8080` یعنی اینباند روی مسیر `/` گوش می‌دهد — یعنی **هر مسیری که در جدول پایین نباشد**. پس مسیر را هرچه دلتان خواست بگذارید. فقط **این عدد را عوض نکنید.**

### گام ۷ — لینک را بگیرید و تست کنید

روی اینباند → کلاینت → **QR Code** یا **Copy Link**. همان را در v2rayNG / Streisand / NapsternetV وارد کنید و وصل شوید.

اگر خواستید همه‌ی کانفیگ‌ها را با یک لینک به بقیه بدهید، از بخش **Subscription** پنل یک لینک ساب بسازید (فرمت آدرس: `https://دامنه‌شما/sub/شناسه`).

## جدول مسیر و پورت اینباندها

اگر چند اینباند می‌خواهید، پورت هر کدام را **دقیقاً** برابر عدد روبه‌روی مسیرش بگذارید:

| مسیر (Path) | پورت اینباند |
|---|---|
| هر مسیر دلخواه (مثل `/cdn`) | **8080** |
| `/in1` | 8081 |
| `/in2` | 8082 |
| `/in3` | 8083 |
| `/in4` | 8084 |
| `/in5` | 8085 |
| `/in6` | 8086 |
| `/in7` | 8087 |
| `/in8` | 8088 |
| `/in9` | 8089 |

### مسیر را چطور انتخاب کنم؟

**روی پورت ۸۰۸۰ کاملاً آزادید** — هر اسمی دوست دارید بگذارید: `/cdn`، `/mysecret`، `/a/b/c`.

روی پورت‌های ۸۰۸۱ تا ۸۰۸۹ مسیر باید با همان پیشوند جدول شروع شود (`/in1` تا `/in9`).
ولی خودِ `/in1` لازم نیست — می‌شود `/in1mobile` یا `/in1/mobile` هم گذاشت، چون تطبیق با پیشوند انجام می‌شود.
همچنین می‌توانید قاطی کنید: یک اینباند روی ۸۰۸۰ با مسیر `/cdn` و یکی روی ۸۰۸۷ با `/in7`.

### ⚠️ سه تله

**۱. پورت ۸۰۸۰ فقط برای یک اینباند است.**
روی آن، مسیری انتخاب نکنید که با `/in1` تا `/in9` شروع شود. مثلاً `/in10` را nginx به پورت ۸۰۸۱ می‌فرستد (چون پیشوند بلندتر برنده است) و هرگز به اینباند شما نمی‌رسد.

**۲. هر اینباند باید پورت جدا داشته باشد.**
هرگز دو اینباند را روی **یک پورت مشترک** با دو مسیر مختلف نسازید. Xray دو سوکت جدا روی آن پورت باز می‌کند و لینوکس هر اتصال را تصادفی به یکی از آن دو می‌دهد — نتیجه این می‌شود که حدود **نصف اتصال‌ها به اینباند اشتباه می‌رسند و کار نمی‌کنند**. یعنی اینباند یک بار وصل می‌شود، یک بار نه. پس حداکثر **۱۰ اینباند** دارید.

**۳. `/managepanel` و `/sub` رزرو هستند.**
این دو مسیر مالِ خود پنل و ساب‌لینک‌اند. روی اینباندها از این دو پیشوند استفاده نکنید یا پنل از دست می‌رود.

**Network را `ws` بگذارید** (پایدارترین حالت). `xhttp` و `httpupgrade` هم تست شده و کار می‌کنند.

### ✅ نکته‌ی مهم درباره‌ی فیلد Host

اگر Network را `ws` گذاشتید و می‌خواهید اتصال از پشت کلادفلر (CDN) رد شود، فیلد **Host** را **خالی** بگذارید. اگر آن را با آدرس دامنه‌ی Railway پر کنید، آن اینباند مستقیم به Railway وصل می‌شود و از کلادفلر عبور نمی‌کند — و اگر شبکه‌ای که با آن تست می‌کنید `railway.app` را ببندد، آن اینباند کار نمی‌کند.

## تست سلامت

آدرس زیر را در مرورگر باز کنید:

```
https://دامنه‌شما/in7
```

| پاسخ | معنی |
|---|---|
| **400** | ✅ عالی — ترافیک به Xray رسیده، مسیر سالم است |
| **404** | ✅ خوب — اینباند بالاست (برای xhttp طبیعی است) |
| **502** | روی آن پورت هنوز اینباند نساخته‌اید |

> روی پنل تازه همه‌ی مسیرها **502** می‌دهند. این کاملاً طبیعی است — یعنی nginx آماده است ولی هنوز اینباندی ساخته نشده.

## چک‌لیست طلایی

بعد از نصب، این‌ها را چک کنید:

- [ ] Target Port دامنه روی **3000** است
- [ ] پسورد پنل را عوض کرده‌اید
- [ ] Volume روی `/etc/x-ui` وصل شده است
- [ ] پنل با `/managepanel/` باز می‌شود
- [ ] بعد از ساخت اولین اینباند، پینگ می‌دهد
- [ ] آی‌پی کاربران در پنل ثبت می‌شود (نه `127.0.0.1`) — محل دیدنش: **Inbounds → دکمه‌ی جزئیات اینباند → کنار نام کاربر**

## اگر مشکلی پیش آمد

| مشکل | راه حل |
|---|---|
| دامنه پنل را باز نمی‌کند | چک کنید آخرین دیپلوی موفق بالا آمده باشد |
| `Application failed to respond` | Target Port دامنه را روی **3000** بگذارید |
| بیلد شکست می‌خورد | هر ۴ فایل را در ریپو چک کنید |
| پنل باز است ولی اینباند وصل نمی‌شود | پورت اینباند را با جدول بالا چک کنید |
| بعد از دیپلوی همه چیز پاک شد | Volume روی `/etc/x-ui` وصل نکرده‌اید |
| بخش IP کاربران خالی است | روی پنل خام تا اولین اتصال طبیعی است. IP فقط وقتی ثبت می‌شود که کاربر **از مسیر همین دامنه** وصل شود و اتصالش چند ثانیه باز بماند (اتصال‌های یک‌ثانیه‌ای ثبت نمی‌شوند). اگر بعد از اتصال طولانی هم خالی بود، یک بار سرویس را Redeploy کنید — خودِ سیستم مسیر IP را خودکار درست می‌کند |
| کانفیگ وصل می‌شود ولی سایتی باز نمی‌شود | فیلد Host اینباند را خالی کنید |
| اینباند یک بار وصل می‌شود، یک بار نه | دو اینباند روی یک پورت مشترک ساخته‌اید — هر اینباند پورت جدا لازم دارد |
| جدول IP پنل خالی است (همه `127.0.0.1` یا خالی) | مقدار `trustedXForwardedFor` نباید آدرس IP باشد؛ باید نام هدر `X-Forwarded-For` باشد |

برای دیدن خطاها: در Railway → سرویس → تب **Deployments** → آخرین دیپلوی → **View Logs**.

## چیزهایی که خودکار انجام می‌شود

### باز شدن پنل با خود دامنه
آدرس دامنه را که باز کنید، خودکار به صفحه‌ی پنل می‌رود — بدون اینکه لازم باشد `/managepanel/` را تایپ کنید.
روی **دامنه‌ی railway.app** و روی **دامنه‌ی کاستوم** هر دو یکسان کار می‌کند.
اگر `/managepanel` را بدون اسلش آخر هم بزنید، به `/managepanel/` می‌رود.

> ⚠️ **توجه امنیتی:** با این تغییر، پنل دیگر «پنهان» نیست. قبلاً هر کسی دامنه را اسکن می‌کرد فقط یک خطای ۵۰۲ می‌دید و نمی‌فهمید پنل کجاست؛ الان صفحه‌ی ورود پنل را می‌بیند. چون پسورد محکم گذاشته‌اید مشکلی نیست، ولی بهتر است بدانید.

### IP واقعی کاربران
چون پنل پشت nginx است، Xray به‌طور پیش‌فرض آی‌پی همه را `127.0.0.1` می‌بیند. برای درست شدن این، دو چیز لازم است و هر دو خودکار انجام می‌شوند:

۱. **nginx** هدر `X-Forwarded-For` را طوری بازنویسی می‌کند که فقط آی‌پی واقعی کاربر داخلش باشد.
۲. **`auto-sockopt.sh`** هر ۲۰ ثانیه دیتابیس را چک می‌کند و روی هر اینباند جدید مقدار `sockopt.trustedXForwardedFor` را می‌گذارد.

**لازم نیست شما کاری بکنید.** آی‌پی کاربرها داخل `Inbounds → کلاینت → IPs` و ستون آی‌پی در پنل دیده می‌شود.

> ⚠️ نکته‌ی فنی: مقدار `trustedXForwardedFor` در Xray **نام یک هدر** است، نه آدرس آی‌پی.
> این فیلد را دستی روی `127.0.0.1` بگذارید Xray هدر را «جعلی» می‌بیند، نادیده می‌گیرد و
> در نتیجه **جدول آی‌پی پنل خالی می‌ماند**. مقدار درست `X-Forwarded-For` است.

### IP Limit
کادر **IP Limit** در تنظیمات کلاینت فعال است و مقدارش ذخیره می‌شود. اگر یک کاربر با چند دستگاه وصل شود و از حد بگذرد، دستگاه مازاد **قطع** می‌شود (اما بلاک دائمی نمی‌شود، چون Railway اجازه‌ی iptables نمی‌دهد).

توصیه: `limitIp` را **۲ یا ۳** بگذارید، نه ۱.

## نمایش اینباندِ هر کاربر در ربات

اگر از ربات مدیریت استفاده می‌کنید، در لیست آنلاینِ ربات **کنار تعداد دستگاه** (`📱N`) نام اینباندی که آن کاربر از آن وصل شده هم داخل باکس نشان داده می‌شود:

```
🟢 نام کاربر · آیدی · 📱1 [2 | هلند 🇳🇱]
```

اگر کاربر هم‌زمان با چند کانفیگ وصل باشد، **همه‌ی اینباندهای فعال** کنار هم می‌آیند.
و اگر دو دستگاه با دو اینباند مختلف وصل باشند، هر کدام در ردیف خودش نمایش داده می‌شود.

### فعال‌سازی (یک متغیر در Railway — دو دقیقه)

این قابلیت با یک **متغیر محیطی** روشن می‌شود؛ **هیچ آدرس یا کلیدی داخل سورس نیست**، پس این سورس را هر جا خواستید می‌توانید بگذارید (حتی عمومی).

| گام | کار |
|---|---|
| ۱ | **آدرس پوش را از ربات بگیرید:** ربات → «🔐 امنیت و کلیدها» → «🔌 رویداد اینباند (پوش پنل)». همان صفحه آدرس کامل را نشان می‌دهد (شکل `https://<worker>/ib?k=<کلید>`). دکمهٔ «♻️ ساخت کلید جدید» هم همان‌جاست. |
| ۲ | Railway → سرویسِ پنل → **Variables** → `New Variable` → نام: `IB_PUSH_URL` · مقدار: همان آدرس. |
| ۳ | **Deploy / Redeploy**. در لاگ‌های سرویس باید ببینید: `✅ تست کلید پوش: موفق`. |

همین. از این به بعد نام اینباند کنار `📱N` می‌آید.

### اگر کلید عوض شود یا اشتباه بگذارید چه می‌شود؟ (مهم)

* این قابلیت **هیچ ربطی به کارکرد پنل و کانفیگ‌ها ندارد**؛ اگر کلید اشتباه باشد فقط **نام اینباند نمایش داده نمی‌شود** و بقیهٔ لیست مثل قبل کار می‌کند.
* پنل در **هر بار بالا آمدن** یک تست کوتاه انجام می‌دهد (`…&selftest=1`) و نتیجه را در لاگ می‌نویسد:
  * `✅ تست کلید پوش: موفق` ⇒ همه‌چیز درست است.
  * `⛔ تست کلید پوش: کلید نامعتبر است` ⇒ مقدار `IB_PUSH_URL` با آدرس فعلی ربات یکی نیست.
  * `ℹ️ تست کلید پوش انجام نشد` ⇒ فقط شبکهٔ خروجی در لحظهٔ بوت آماده نبود؛ ایرادی نیست.
* ربات هم در `/diag` دو نشانه دارد: `inboundEvents.badKeys` (تعداد درخواست‌های کلید-اشتباه) و هشدار `ib_push_silent` (اگر بیش از ۲۴ ساعت هیچ رویدادی نرسد). یعنی این بخش دیگر **بی‌صدا** خراب نمی‌شود.
* **راه‌حل همیشگی:** آدرس تازه را از همان منوی ربات بگیرید و مقدار `IB_PUSH_URL` را در Railway به‌روز کنید → Redeploy.

### خاموش کردن

مقدار متغیر را بگذارید `off` (یا متغیر را نسازید/پاک کنید). در لاگ می‌بینید:
`⚪️ رویدادهای اینباند: خاموش (متغیر IB_PUSH_URL ست نشده)` — رفتار پنل دقیقاً مثل قبل می‌شود و هیچ درخواستی به بیرون نمی‌رود.

### چطور کار می‌کند؟

nginx در لحظه‌ی **باز شدن** هر تونل یک درخواست بسیار کوتاه به ربات می‌فرستد و در لحظه‌ی **بسته شدن** هم یکی دیگر. داخل آن درخواست فقط سه چیز است: مسیر درخواست، آی‌پی واقعی کاربر، و دامنه‌ای که کاربر با آن وصل شده. ربات خودش:
- دامنه را به پنل مربوطه نسبت می‌دهد (دامنه‌ی پنل یا دامنه‌ای که داخل تنظیمات خودِ اینباند نوشته شده — هر کدام که کاربر با آن وصل شود)،
- مسیر را به **نام** اینباند تبدیل می‌کند (نام را لحظه‌ی نمایش از خود پنل می‌خواند).

### نکته‌ها

- اگر ربات در دسترس نباشد یا خاموش باشد، **هیچ اتفاقی برای تونل‌ها نمی‌افتد**؛ درخواست پوش کاملاً جدا از مسیر کاربر است و مهلتش ۶ ثانیه است.
- سرعت و ترافیک کاربر هیچ تأثیری نمی‌بیند (فقط یک درخواست چند صد بایتی در لحظه‌ی باز/بسته شدن).
- اگر چند نفر پشت یک آی‌پی باشند (NAT)، مثل شمارش دستگاه‌ها ممکن است نسبت‌دهی جابه‌جا شود.
- این قابلیت فقط با **نسخه‌ی جدید ربات** نمایش داده می‌شود؛ روی ربات قدیمی فقط باکس نام نمی‌آید و بقیه‌ی لیست مثل قبل کار می‌کند.
- 🔐 در این سورس **هیچ کلید یا آدرسی نیست**؛ آدرس پوش فقط از متغیر `IB_PUSH_URL` خوانده می‌شود، پس سورس قابل اشتراک‌گذاری است. خودِ کلید را جایی منتشر نکنید (فقط در Variables بماند).

## آپدیت به نسخه‌ی جدید 3x-ui

در فایل `Dockerfile`، خط زیر را پیدا کنید:

```dockerfile
ARG XUI_VERSION=3.8.5
```

عدد را به نسخه‌ی جدید عوض کنید، Commit بزنید — Railway خودش دوباره بیلد می‌کند. تمام تنظیمات پنل شما دست‌نخورده می‌ماند.

## مشخصات فنی

| بخش | مقدار |
|---|---|
| پورت nginx (دامنه) | 3000 |
| پورت پنل | 2053 — مسیر `/managepanel/` |
| پورت ساب‌لینک | 2096 — مسیر `/sub/` |
| پورت اینباند پیش‌فرض | 8080 — مسیر `/` |
| اینباندهای اضافی | 8081 تا 8089 — مسیرهای `/in1` تا `/in9` |
| تایم‌زون | Asia/Tehran |

**خیلی کوتاه:** nginx روی پورت ۳۰۰۰ می‌نشیند، مسیر `/managepanel/` را به پنل می‌فرستد، `/sub/` را به ساب‌لینک، و بقیه‌ی مسیرها را به اینباندها. همه زیر یک پورت.
